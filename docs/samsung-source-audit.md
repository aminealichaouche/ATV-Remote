# Samsung source audit

Audit date: 12 October 2026. Target: an iPhone application on iOS 27 controlling the user's Samsung TV locally, without a companion server. The user sees `S95BD` on their phone; preserve that displayed name. Read the TV's reported hardware model and firmware during setup before claiming compatibility, rather than assuming it means S95B or S95D.

## Decision

Do not use `pedrinho/samsung_remote` as an application foundation. It is a Python command-line wrapper with a broken published dependency contract, no iOS application layer, and no suitable persistent connection, pairing, or credential model. Its key names and basic discovery concepts are useful reference material.

`TVCommanderKit` and `smart-tv-remote-swift` demonstrate native Swift control over Samsung's local port-8002 WebSocket. Neither is approved unchanged for the intended app. Prefer a small Samsung adapter implemented as a Swift actor with an explicit pairing state machine, Keychain storage, host-scoped certificate trust, cancellation/deadlines, and a serial command queue. Use the audited protocol payloads as references and preserve the notices of any copied code.

## Supplied Python repository

### SAM-01 — P1: published dependencies do not match the source API

[pyproject.toml:12](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/pyproject.toml#L12) names nonexistent `README.rst`; lines 15–17 pin Samsungctl 0.7.0, websocket-client 0.44.0 and upnpclient 0.0.6. [requirements.txt:3](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/requirements.txt#L3) instead requires `samsungctl>=0.8.0b0`. The public PyPI version metadata checked during this audit lists releases through 0.7.1, with no 0.8 release. These two installation paths cannot supply the same API.

[helpers/tvcon.py:31](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/helpers/tvcon.py#L31) calls `samsungctl.Config`, which the actual published 0.7.0 source does not expose. An offline probe using that source confirmed the call returns False before any socket is opened. Patching tests with a mocked `Config` does not establish dependency compatibility.

Resolution if maintaining the CLI: fix package metadata, select one supported, immutable dependency revision, and test against its real API. For the iOS app, implement native networking instead of embedding this wrapper and a Python runtime.

### SAM-02 — P1: no persistent pairing/credential contract for a modern TV

[samsung_remote.py:20](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/samsung_remote.py#L20) defaults to `port=55000`, `method='websocket'`, `timeout=0`; the CLI only changes host and legacy mode. [helpers/tvcon.py:31](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/helpers/tvcon.py#L31) creates a fresh Config and Remote for every key and passes no token, paired flag, saved-config path, certificate policy or known MAC. The configured object is discarded after each call. There is no UI-visible pair/reject/expiry workflow.

55000 is the legacy TCP port; modern Samsung control uses 8001/8002. The newer kdschlosser fork can override the supplied port internally in `RemoteWebsocket.open`, so the wrong default is not proof that every fork-based attempt fails. It is still an inconsistent configuration and its behavior depends on an unpinned dependency. The definitive failure with the published pin is SAM-01.

Resolution: retain one authenticated connection per selected device; save the returned token in Keychain; use a bounded pairing state machine and explicit Wake-on-LAN support where the TV supports it. Do not present `KEY_POWERON` alone as proof the TV can be woken from standby.

### SAM-03 — P2: the suggested fork writes pairing tokens to the default log and disables TLS verification

[samsung_remote.py:81](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/samsung_remote.py#L81) enables root DEBUG file logging to `app.log`. The GitHub fork recommended by the README logs saved/new tokens at [remote_websocket.py:70](https://github.com/kdschlosser/samsungctl/blob/febcb5176089f422599768a337029f990bd48871/samsungctl/remote_websocket.py#L70), lines 122/134, and whole incoming messages at line 391. These messages include pairing responses. The same dependency sets `ssl.CERT_NONE` at line 74.

This path exposes local control credentials in a normal debug log and does not authenticate the TV certificate. The root repository itself does not implement a credential store or certificate verification override; these behaviors belong to its suggested dependency workaround.

Resolution: redact tokens and query strings, disable sensitive DEBUG logs, pin a peer certificate after a user-approved first pairing or use a narrowly scoped, documented trust policy, and explicitly reset/re-pair on peer identity change.

### SAM-04 — P2: discovered locations are fetched without endpoint or response bounds

[helpers/ssdp_custom.py:94](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/helpers/ssdp_custom.py#L94) accepts UDP response locations without validating the sender/service. [helpers/tvinfo.py:72](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/helpers/tvinfo.py#L72) obtains an IP by searching anywhere in the URL, then passes the original URL to `urlopen` and reads the entire response at lines 80–84. An IPv4 string in a path does not establish that the URL host is that device. The code imposes no HTTP-only scheme restriction, LAN-host binding, redirect restriction, response-size limit or device-description limit.

A device on the LAN can supply a misleading location and cause requests to other endpoints or resource exhaustion. The source does not establish internet exposure, arbitrary code execution, or an external-entity XML vulnerability; those are not claimed here.

Resolution: parse URLs structurally, bind them to the discovered peer, reject unsupported schemes/hosts/redirects, cap bytes and response time, then parse and validate manufacturer/model/device identity. Keep manual IP entry available.

### SAM-05 — P2: success reporting is not tied to command outcome

[helpers/tvcon.py:41](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/helpers/tvcon.py#L41) ignores the result of `control` and returns True if no exception bubbles out. An offline mock probe confirmed a False control result is reported as True. In the suggested fork, some power/offline paths return without establishing that the requested state was reached. [samsung_remote.py:254](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/samsung_remote.py#L254) and line 269 ignore the helper result, so a failed key or macro can exit with status 0.

Resolution: distinguish queued/sent/confirmed/rejected/offline states. Make CLI failure return a nonzero status, and have the native UI show transport/auth errors. A completed WebSocket write is not proof that a TV applied a key.

### SAM-06 — P3: timeout, parser and test gaps

- [helpers/ssdp.py:55](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/helpers/ssdp.py#L55) uses the real Netdisco module-level `scan` API; that API exists. However caller deadlines/retries are deliberately ignored, and the wrapper does not deduplicate repeated Samsung services by device identity. Netdisco's maintainer archived/deprecated the dependency in 2021.
- [helpers/ssdp_custom.py:72](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/helpers/ssdp_custom.py#L72) changes the process-wide default socket timeout. Line 40 assumes cache-control contains `=`, and malformed response parsing at lines 99–101 stops the current receive loop. Use per-socket deadlines and ignore malformed individual responses.
- [helpers/tvinfo.py:33](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/helpers/tvinfo.py#L33) chooses protocol from the fifth model character. This assumes one historical model-number layout and treats H/J as ordinary WebSocket models, despite encrypted variants. Detect advertised capabilities, not a single character.
- [helpers/macro.py:46](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/helpers/macro.py#L46) gives DictReader explicit field names, so a `key,wait` header becomes a command. Lines 60–68 accept negative, non-finite or arbitrarily large waits and unvalidated key strings. Validate the entire macro before sending its first key; bound length and delays.
- [samsung_remote.py:180](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/samsung_remote.py#L180) calls `print_help` on an argparse Namespace. A no-argument invocation raises AttributeError; the test substitutes a MagicMock Namespace that hides the defect. Several edge tests explicitly accept invalid input, and the named integration test mocks the TV. These tests are not evidence of an S95-series connection.
- [run_tests.py:15](https://github.com/pedrinho/samsung_remote/blob/2c561a699045159b6447f8165abcdcb893fdd601/run_tests.py#L15) automatically installs unpinned test dependencies if pytest is absent. It was not run. Its subprocess calls use argument arrays; no production shell execution, `eval`, or shell-injection sink was found in the inspected wrapper.

## Validation and native implementation requirements

Five Python checks ran with socket creation and URL network access explicitly blocked: published 0.7.0 Config incompatibility, 55000 default propagation, ignored False control result, no-argument Namespace crash, and normal return after a failed CLI key. Two Swift model/extension source files were compiled independently to check command serialization, URL escaping and invalid-MAC packet generation. SmartCast's 12 offline upstream tests passed. No full Python upstream-suite success is claimed.

For the application design:

1. Keep Samsung endpoints and tokens separate from Apple TV credentials. Store each pairing credential in Keychain under a stable device identity, never in URLs included in logs or exported diagnostics.
2. Use a Samsung actor with `disconnected → connecting → awaitingApproval → ready` and explicit denied/timeout/revoked states. Complete pairing only after the correct event; discard outdated callbacks and pending commands when the connection changes.
3. Build URLs with URLComponents and encode the exact Samsung wire types from a hardware-tested fixture. Restrict the self-signed certificate exception to the explicitly selected, paired TV; avoid a global trust-all delegate or global ATS exception.
4. Start with manual IP plus narrowly scoped Samsung SSDP discovery. Honor Apple's local-network privacy requirements and determine multicast/broadcast entitlement requirements from the chosen iOS networking implementation. The candidate README's Bonjour keys alone are not proof SSDP/broadcast permission is handled.
5. Use a bounded, serial key queue with repeat throttling, press/release tracking, finite deadlines, reconnect cancellation and foreground/resume handling. Surface authentication/connection status rather than assuming every key succeeded.
6. Treat wake, discrete power, HDMI source selection, text entry and CEC forwarding as capability-dependent features. Validate these on the actual S95 model, firmware and network before promising them. A Samsung WebSocket Home key targets Samsung Home; it is not a direct Apple TV Home API.

Primary behavior references: [maintained samsungtvws](https://github.com/xchwarze/samsung-tv-ws-api), [Home Assistant Samsung integration](https://www.home-assistant.io/integrations/samsungtv), [Apple's TV remote/HDMI-CEC documentation](https://support.apple.com/guide/tv/use-other-remotes-to-control-apple-tv-4k-atvb0410f604/tvos), and [Samsung Anynet+ documentation](https://www.samsung.com/ca/support/tv-audio-video/anynet-hdmi-cec-on-your-samsung-tv/). These establish available mechanisms, not successful control of the user's untested hardware.
